## User Constraints (from CONTEXT.md)

### Locked Decisions

**Scenario coverage:**
- E2E pairing test — automated; test injects the pairing token directly (bypasses QR camera scan) to drive the full handshake over a real USB/AWDL connection. Manual QR pairing remains a valid one-time human flow but is not automated.
- USB→AWDL fallback — semi-automated on-device UI test with a "Unplug USB now" prompt; human unplugs cable, test measures switchover time and asserts AWDL took over. A fully-automated path (via USB hub relay or usbmuxd device removal simulation) is planned for the future but not required in this phase.
- Latency benchmarks — included; send a burst of N messages over real USB, measure round-trip time distribution, assert p99 < 50ms. Regression signal for protocol performance.
- 4 named regression tests — one per bug fixed in commit 9046927: (1) decoder missing for unpaired USB connection, (2) pairingCompleted ignored in pendingUSBIdentity state, (3) pairing response silently dropped, (4) iOS sending sessionResume before pairing completes. Each test has a descriptive name and runs against real connections.

**Test architecture:**
- Transport layer — tests use the same transport as the app (existing pairing/session protocol). No separate test control channel. Tests run inside a linked test target or live app process; the Mac agent is discovered via the normal USB/AWDL connection path.
- Mac test mode — agent supports a `--test-mode` launch flag that enables: faster timeouts (2s reconnect vs 30s), verbose wire logging to stdout (every framed message with timestamps), TestReset handling without Keychain write (memory-only, avoids polluting real Keychain), deterministic incrementing connection IDs (conn-1, conn-2, ...).
- Test targets — both: a new `KeydIntegrationTests` XCTest target (CI-compatible, runs via `xcodebuild test` on device) and a "Suite C: Connected" section in the existing `TransportTestRunnerView` on-device UI. They share the same test case implementations.
- State reset — iOS test drives a `TestReset` protocol message; Mac agent clears pairing state from memory (no Keychain write in test mode) and acks before the test proceeds. Additional `ForceState` commands added only if a specific regression test proves it necessary.

**Invocation & reporting:**
- CLI entry point — `make test-integration`; Makefile kills any running agent, starts a fresh instance with `--test-mode`, runs the XCTest suite on the connected device via xcodebuild, streams results, tears down agent when done.
- Semi-automated tests — on-device UI only (Suite C in TransportTestRunnerView). XCTest target runs fully-automated tests only; no XCTestCase waits for human actions.
- Failure output — on test failure, dump the full wire log (every message sent/received on both sides with timestamps) sufficient to reconstruct what happened without a debugger.
- Deploy gate — `make deploy` runs `make test-integration` as a prerequisite; deploy is blocked if any XCTest integration test fails. On-device semi-automated tests are advisory only and never block deploy.
- deploy-and-run.sh — add a `test-integration` mode (alongside existing `run`/`attach`) that handles agent start in test mode and xcodebuild test invocation. Wired through Makefile `test-integration` target.

**Mac-side harness:**
- `--test-mode` flag scope: faster timeouts + verbose wire logging to stdout + TestReset without Keychain write + deterministic connection IDs (all four).
- Start with `TestReset` message only for state setup. Add `ForceState` or additional test commands only when a specific regression proves it necessary.

### Claude's Discretion

- How token injection bypasses QR for the automated pairing test (direct call to the pairing completion handler vs. mock QR scanner)
- JSON trace format for Suite C on-device results (extend existing TransportTestRunner format)
- xcodebuild test invocation flags and result bundle path

### Deferred Ideas (OUT OF SCOPE)
- Fully-automated USB→AWDL fallback via USB hub relay or usbmuxd device removal simulation — noted for future, not this phase
- CI lane with tethered device — would use `make test-integration` as the command, but CI infrastructure setup is out of scope here

## Summary

Phase 01.1 adds a second test tier that requires real hardware (iPhone + Mac connected via USB or AWDL). The Phase 1 FSM unit tests in SharedProtocol (73 tests) run without hardware; this phase adds connected tests that exercise the actual usbmuxd TCP tunnel, Bonjour AWDL discovery, pairing handshake, and message round-trips. The four interlocking bugs from commit 9046927 (decoder missing for unpaired USB, pairingCompleted ignored in pendingUSBIdentity, pairing response silently dropped, iOS sessionResume sent before pairing completes) are the primary regression targets.

The architecture pattern centers on two complementary test surfaces that share implementation: a `KeydIntegrationTests` XCTest target that `xcodebuild test` runs on the physical device (fully automated, blocks deploy), and a "Suite C: Connected" section in the existing on-device `TransportTestRunnerView` UI (semi-automated, advisory only). The Mac agent gains a `--test-mode` launch flag that enables four behaviors: 2s timeouts, verbose wire logging, TestReset without Keychain writes, and deterministic connection IDs. The iOS test drives the flow by sending a `TestReset` message over the real connection before each test case, receives an ack, then proceeds.

The test harness does NOT use a separate out-of-band control channel — it uses the same length-prefixed binary framing (4-byte big-endian + JSON payload) that the production app uses. This means `TestReset` and `TestResetAck` are new `KeydMessage` enum cases added to `SharedProtocol/Sources/SharedProtocol/Messages.swift`. The Makefile `test-integration` target becomes the single developer entry point: it kills any running agent, starts a fresh `--test-mode` instance, runs xcodebuild test on the connected device, and tears down the agent.

**Primary recommendation:** Add `TestReset`/`TestResetAck` to `KeydMessage`, implement `--test-mode` in the macOS agent, create `KeydIntegrationTests` XCTest target via `project.yml`, write 6 XCTest methods covering the 4 regression cases + pairing flow + latency benchmark, wire `make test-integration` with `scripts/deploy-and-run.sh test-integration` mode, and add the Suite C section to `TransportTestRunnerView`.

### Pattern 1: --test-mode Flag Detection in macOS Agent

**What:** `AppDelegate.applicationDidFinishLaunching` checks `ProcessInfo.processInfo.arguments` for `--test-mode` before constructing `TransportManager`. A `TestMode` struct is passed through to components that need altered behavior.

**When to use:** Every launch; flag is absent in production, present during `make test-integration`.

**Example:**
```swift
// Source: ProcessInfo docs + project pattern (AppDelegate.swift)
func applicationDidFinishLaunching(_ notification: Notification) {
    let isTestMode = ProcessInfo.processInfo.arguments.contains("--test-mode")
    let testMode = isTestMode ? TestMode() : nil

    let manager = TransportManager(
        injectionRouter: injector,
        statusBar: statusBar,
        pairingManager: pairingManager,
        testMode: testMode
    )
    // ...
}

struct TestMode {
    let reconnectTimeout: TimeInterval = 2.0   // vs 30.0 in production
    let verboseWireLog: Bool = true
    var connectionCounter: Int = 0             // conn-1, conn-2, ...
    var isPaired: Bool = false                 // in-memory only; no Keychain writes
}
```

### Pattern 2: TestReset Message Flow

**What:** iOS XCTest sends `.testReset` over the active connection. Mac agent (in test mode) clears in-memory pairing state and sends `.testResetAck`. iOS test `await`s the ack before proceeding. This is the synchronization barrier between test cases.

**When to use:** At the start of every integration test case that needs a clean slate.

**Example:**
```swift
// KeydIntegrationTests/IntegrationTestRunner.swift
// Source: XCTest async/await pattern (Apple documentation)

func testPairingOverUSB() async throws {
    // 1. Send TestReset, wait for TestResetAck
    try await harness.sendAndAwait(.testReset, expecting: .testResetAck, timeout: 5.0)

    // 2. Inject pairing token directly (bypass QR scan)
    let token = PairingToken(publicKey: testPublicKey, deviceID: testDeviceID)
    harness.injectPairingToken(token)

    // 3. Observe session established
    let state = try await harness.awaitState(.sessionEstablished, timeout: 10.0)
    XCTAssertEqual(state, .usbConnected)
}
```

### Pattern 3: Shared Test Case Implementations

**What:** `IntegrationTestCase.swift` (in the KeydApp target, not KeydIntegrationTests) contains the actual test logic as `async` methods. Both `KeydIntegrationTests` XCTest target and Suite C in `TransportTestRunnerView` call the same methods — XCTest via `XCTestCase.addTeardownBlock`, Suite C via direct `await`.

**When to use:** Ensures Suite C and XCTest run identical scenarios. Prevents divergence.

**Example:**
```swift
// KeydApp/Debug/IntegrationTestCase.swift
// Shared between XCTest target and on-device UI runner

struct IntegrationTestCase {
    static func runPairingTest(harness: IntegrationHarness) async throws -> IntegrationResult {
        try await harness.reset()
        harness.injectPairingToken(testToken)
        let sessionState = try await harness.awaitMessage { msg in
            if case .sessionEstablished = msg { return true }
            return false
        }
        return IntegrationResult(passed: sessionState != nil, detail: nil)
    }
}
```

### Pattern 4: xcodebuild On-Device Test Invocation

**What:** `scripts/deploy-and-run.sh test-integration` mode builds `KeydIntegrationTests`, starts the Mac agent with `--test-mode`, then runs `xcodebuild test` targeting the physical device.

**When to use:** Called by `make test-integration`.

**Example:**
```bash
# scripts/deploy-and-run.sh test-integration mode

# Kill existing agent
pkill -x KeydAgent 2>/dev/null || true
sleep 1

# Start agent in test mode (background, stdout goes to log file)
"$mac_binary" --test-mode > "$session_dir/agent-testmode.log" 2>&1 &
echo $! > "$meta_dir/agent.pid"
sleep 2  # give agent time to bind listeners

# Run XCTest on device
xcodebuild test \
    -workspace "$workspace_abs" \
    -scheme KeydIntegrationTests \
    -destination "platform=iOS,id=$IPHONE_DEVICE" \
    -resultBundlePath "$session_dir/integration.xcresult" \
    -derivedDataPath "$derived_data_abs"

# Teardown agent
kill "$(cat "$meta_dir/agent.pid")" 2>/dev/null || true
```

**Note:** `platform=iOS,id=DEVICE_UUID` is the correct destination specifier for physical devices in xcodebuild (confirmed from Apple developer docs and xcodebuild man page). The device UUID comes from `IOS_DEVICES` or `IPHONE_DEVICE` env vars already used by the existing Makefile.

### Pattern 5: Wire Log Capture on Failure

**What:** In `--test-mode`, every message sent and received is written to stdout with microsecond timestamps. The `deploy-and-run.sh test-integration` mode captures this to `agent-testmode.log`. On XCTest failure, the test dumps its client-side event trace as an XCTest attachment.

**When to use:** XCTest failure — the combined agent log + iOS attachment gives a complete wire reconstruction without a debugger.

**Example:**
```swift
// On test failure, attach the wire log
func attachWireLog(_ log: [IntegrationEvent]) {
    let data = try? JSONEncoder().encode(log)
    let attachment = XCTAttachment(data: data ?? Data())
    attachment.name = "wire-log.json"
    attachment.lifetime = .keepAlways
    add(attachment)
}
```

### Anti-Patterns to Avoid

- **Out-of-band control channel:** Don't create a second TCP port for test commands. The existing 4-byte-framing + JSON protocol is the control channel. `TestReset` is just another `KeydMessage` case.
- **XCTestCase waiting for human input:** The CONTEXT.md is explicit — no `XCTestCase` method waits for human actions. USB→AWDL semi-automated tests live only in Suite C (on-device UI).
- **Keychain writes in test mode:** Mac agent test mode must use in-memory pairing state only. Writing to Keychain in tests pollutes the production pairing state.
- **Hardcoded device IDs:** The test target must use the same `IPHONE_DEVICE`/`IOS_DEVICES` env vars as the existing `make run` flow — don't hardcode UDIDs.
- **`open` to launch test-mode agent:** `open -n "$mac_app_bundle"` cannot pass custom arguments. Use the binary directly (`"$mac_binary" --test-mode &`) when starting in test mode.
- **Starting deployment before agent binds:** After launching `KeydAgent --test-mode`, add a brief sleep (1-2s) before running xcodebuild test so the agent has time to bind its USB and AWDL listeners.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Running tests on device | Custom test executor | `xcodebuild test -destination "platform=iOS,id=..."` | Apple's official tool; handles code signing, test discovery, result bundles |
| Parsing test results | Custom xcresult parser | stdout `-quiet false` streaming + `xcodebuild` return code | Return code 0/non-0 is sufficient for the deploy gate; stdout gives human-readable output |
| Async test synchronization | Custom wait loops with sleep | `XCTestExpectation` / `await fulfillment(of:timeout:)` | XCTest has built-in async await support since Xcode 14.3; mixing with `waitForExpectations` causes hangs |
| Message serialization for TestReset | Custom binary format | Reuse existing `KeydMessage` JSON encoding + 4-byte framing | The existing `MessageEncoder`/`MessageDecoder` pair handles framing; `TestReset` is just another case |
| Device UUID discovery | Custom device enumeration | `xcrun devicectl list devices` / existing `IPHONE_DEVICE` env var | Already solved in device-config.mk; tests reuse the same variable |

**Key insight:** The project already has all the hard infrastructure — transport, encoder/decoder, FSM, `deploy-and-run.sh` patterns. This phase is adding test cases and two entry points (`--test-mode` flag, `TestReset` message), not building new infrastructure.

## Common Pitfalls

### Pitfall 1: `open` Cannot Pass Launch Arguments to App Bundle
**What goes wrong:** `launch_mac_app()` in `deploy-and-run.sh` uses `/usr/bin/open -n "$mac_app_bundle"` — this cannot pass `--test-mode`. The agent starts without test mode enabled.
**Why it happens:** `open` passes arguments to the OS app launcher, not to the binary's `CommandLine.arguments`.
**How to avoid:** In the `test-integration` mode of `deploy-and-run.sh`, launch the binary directly: `"$mac_binary" --test-mode > "$log" 2>&1 &`. This bypasses `open` entirely.
**Warning signs:** `ProcessInfo.processInfo.arguments` doesn't contain `--test-mode` at agent startup even though you passed it via Makefile.

### Pitfall 2: Agent Already Running When test-integration Starts
**What goes wrong:** A production agent is running on port 12345. The test-mode agent fails to bind the USB listener.
**Why it happens:** Developer ran `make run` earlier and didn't `make stop`.
**How to avoid:** The `test-integration` mode in `deploy-and-run.sh` must `pkill -x KeydAgent` before launching the test-mode instance. The Makefile `test-integration` target should also call `stop` first.
**Warning signs:** Agent log shows "Failed to start listeners: NWError(errorCode: ...)".

### Pitfall 3: Keychain Pairing State Leaks Between Test Cases
**What goes wrong:** Test case 1 pairs, writes to Keychain. Test case 2 starts in a "dirty" paired state — `TestReset` only clears in-memory state in test mode, not Keychain. Test case 2 sees unexpected `sessionResume` behavior.
**Why it happens:** `PairingManager` reads Keychain at launch; if a previous test wrote to Keychain (not test mode), state persists across agent restarts.
**How to avoid:** In `--test-mode`, `PairingManager` must not write to Keychain on `pairingCompleted`. Use a separate `inMemoryPairedDeviceID` property. `TestReset` clears only this in-memory state.
**Warning signs:** Second test run succeeds when first fails; test order dependency.

### Pitfall 4: USB Identity Timeout Fires Before iOS Test Sends Identity
**What goes wrong:** In production, USB identity timeout is ~10s. In test mode it's 2s. If the XCTest setup overhead (app launch, connection establishment) takes longer than 2s, the timeout fires before the iOS side sends `sessionResume` or `pairingRequest`.
**Why it happens:** 2s is fast for a production reconnect but may be too fast if the iOS app under test is cold-starting.
**How to avoid:** The 2s timeout applies to the identity window AFTER the connection is established, not from app launch. But verify the first test case can complete identity within 2s on real hardware. If not, use 5s.
**Warning signs:** First test always fails with "USB identity timeout" in the wire log; subsequent tests pass (app already running).

### Pitfall 5: `xcodebuild test` Cannot Find Scheme `KeydIntegrationTests`
**What goes wrong:** `xcodebuild test -scheme KeydIntegrationTests` reports "scheme not found".
**Why it happens:** After adding the target to `project.yml`, `xcodegen` must be run to regenerate the `.xcodeproj`. If not run, the scheme doesn't exist. Also, the scheme must be marked as shared in Xcode.
**How to avoid:** After editing `project.yml`, always run `xcodegen generate`. Add `xcodegen generate` as a step in the `test-integration` flow (or document it in CONTRIBUTING). The `project.yml` `scheme:` key auto-creates a shared scheme.
**Warning signs:** "xcodebuild: error: The scheme 'KeydIntegrationTests' does not exist."

### Pitfall 6: `XCTestExpectation` + async/await Mixing Hang
**What goes wrong:** Mixing `waitForExpectations(timeout:)` with `async` test methods causes hangs in XCTest on Xcode 14+.
**Why it happens:** `waitForExpectations` spins the runloop; in an async context this deadlocks with the Swift concurrency runtime.
**How to avoid:** Use only `await fulfillment(of:timeout:enforceOrder:)` in async test methods. Never mix `waitForExpectations` with `async throws` test methods.
**Warning signs:** Test hangs indefinitely and times out at the Xcode level rather than at the assertion level.

### Pitfall 7: Wire Log Is Too Noisy for Diagnosis
**What goes wrong:** Verbose wire logging in `--test-mode` captures every heartbeat, making failure diagnosis hard.
**Why it happens:** `transportHeartbeat`/`transportHeartbeatAck` are sent every few seconds — they're noise during a 5s test.
**How to avoid:** Filter heartbeat messages from the default stdout wire log in test mode (log at DEBUG level only), or tag them as `[HB]` for easy grep filtering.
**Warning signs:** Wire log has hundreds of `[HB] transportHeartbeat` lines obscuring the actual failure.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|---|---|---|---|
| ios-deploy for device interaction | `xcrun devicectl` | Xcode 15 / iOS 17 | ios-deploy doesn't work on iOS 17+ physical devices |
| `waitForExpectations(timeout:)` | `await fulfillment(of:timeout:enforceOrder:)` | Xcode 14.3 | Mixing the old API with async hangs the test |

| `open -n app.bundle` for all launch modes | Direct binary launch for test mode | This phase (new) | `open` cannot pass custom `CommandLine.arguments` to the process |

**Deprecated/outdated:**
- `waitForExpectations(timeout:)` in async test methods: causes hangs in XCTest on Xcode 14.3+. Use `await fulfillment(of:timeout:enforceOrder:)` exclusively.
- `XCUIApplication().launchArguments` pattern: this is for UI tests that launch a fresh app process. Integration tests run inside the app process; `ProcessInfo.processInfo.arguments` is the correct read path.

## Open Questions

1. **Pairing token injection mechanism**
   - What we know: The pairing flow calls `PairingManager.completeQRPairing(payload:)` when the QR scanner detects a code. The `QRPayload` contains the Mac's Curve25519 public key.
   - What's unclear: The cleanest injection point — whether to call `completeQRPairing` directly from the test harness (requires the pairing manager to be accessible), or to mock the QR scanner at the `AVCaptureMetadataOutput` level.
   - Recommendation: Direct call to `completeQRPairing(payload:)` from the test harness. The Mac shows a QR code that encodes the payload; in test mode the iOS harness constructs a `QRPayload` from the `--test-mode` agent's public key (obtained via a `TestHello` message or pre-shared in test configuration). This is the cleanest approach — no mocking required.

2. **How iOS XCTest discovers the Mac agent's address for USB**
   - What we know: USB uses a fixed port (12345) via usbmuxd TCP tunnel. The existing `USBTransport` in `KeydApp` connects to `127.0.0.1:12345` when a USB connection is detected.
   - What's unclear: Does the XCTest target (running inside the KeydApp process via `dependencies: - target: KeydApp`) inherit the app's existing transport connection, or must it establish its own?
   - Recommendation: The XCTest target links against `KeydApp` target. Tests call into the app's existing transport manager (already connected in background). The integration test harness wraps the existing `TransportManager` singleton rather than creating a new connection. This avoids port conflicts.

3. **p99 latency measurement methodology**
   - What we know: Target is p99 < 50ms for a burst of N messages over USB. Round-trip is iOS→Mac→iOS.
   - What's unclear: How large N must be for a statistically meaningful p99 (likely 100+), and whether Mac needs to echo messages back or whether the latency is one-way.
   - Recommendation: For the regression signal purpose of this phase, use 100-message burst, measure iOS-side round-trip time (send timestamp to receive timestamp of echo), report p50/p95/p99. The Mac echoes `keyEvent` messages back as `transportHeartbeatAck` (or a new `echo` message type). Set initial threshold at 50ms p99 — adjust down if hardware consistently shows 10-15ms.

4. **xcodegen availability in the developer environment**
   - What we know: `project.yml` is used for both `KeydApp` and `KeydAgent`; xcodegen is the implied tool.
   - What's unclear: Whether xcodegen is in PATH or installed as a build tool.
   - Recommendation: Check `which xcodegen` in `make test-integration` preamble; if missing, emit a clear error message pointing to `brew install xcodegen`.
